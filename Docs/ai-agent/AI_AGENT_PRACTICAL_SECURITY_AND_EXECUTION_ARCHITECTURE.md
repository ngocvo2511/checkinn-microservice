# Practical AI Agent security and execution architecture

Decision, 24/11/2026: use KISS/YAGNI with explicit trust boundaries. CheckInn is a booking application with an assistant, not an LLM governance platform. This decision supersedes mandatory signed setup **only for local synthetic evaluation**; historical reports remain intact. No frontend/backend integration is implemented here.

|Environment|Admission and credential|Execution and data|Governance|
|---|---|---|---|
|Local development evaluation|Explicit standalone developer CLI, default offline, backend process GEMINI_API_KEY|Pinned synthetic allowlist/oracle, fixed HTTPS/model/schema, sequential finite run, request/token rolling limiter, 10s calls, cancellation, zero retries, safe reports; no domain clients|No Ed25519, signing key, trust-root setup, signed approval or financial allocation required. Free Tier is developer-attested for synthetic evaluation only.|
|Development/staging integration (future)|Existing CheckInn authentication/JWT and Gateway routing; backend verifies conversation ownership and roles, keeps key server-side|Typed conversation state and revisions, synthetic/test data, READ allowlist, policy admission, grounding from fresh evidence, bounded turns/tokens/requests, timeouts/cancellation and standard safe logging|No manual approval per chat. Integration and authenticated ingress need their own implementation/validation.|
|Production (future)|Existing user authentication/authorization and conversation ownership; service identity where required by downstream boundary; backend-only provider key|A01–A10 READ allowlist, PolicyExecutor, GroundingGate, typed state/provenance/trusted selections, fresh READ evidence, per-user rate limits, global provider quota controls, turn budgets, deadlines/cancellation, monitoring, privacy minimization and kill switch|Privacy/data-processing approval is separate. Free Tier availability does not approve real customer data. Distributed quota coordination is justified only when actual replicas/traffic need it.|

Ordinary chat is authorized by the application's authenticated user/session and resource ownership, then restricted by policy and grounded evidence. A developer or end user signing each chat request, a financial approval artifact per conversation or a manual billing ceremony per chat would not replace those controls and is unnecessary here.

Existing ordinary constraints stay turn≤30s, model≤3, tool rounds≤2, proposals≤6, HTTP attempts≤6, tool deadline≤10s, retry0. Model output is untrusted and cannot mint USER_CONFIRMED, hotel/room identities, selected-target capabilities or WRITE authority. Provider failure/unknown data stays unknown. The evaluation campaign budget must never become a chat-turn budget.

Signed operator/campaign/allocation components remain optional for externally administered campaigns requiring independently verifiable scope, multiple operators or audit allocation across trusted JVMs. Their validators are unchanged. Do not bulk-delete them: current tests and signed tooling use them. They are not wired into ordinary Agent chat, and local execution no longer calls their admission/financial reservation methods.

Local limits are in-process safeguards, not an account-wide quota/billing guarantee across unrelated processes. CREATE_NEW result files prevent accidental evidence overwrite; they are not distributed IAM, tamper-resistant storage, an invoice or resumable quota grants. Do not restart/split runs to evade this task's70-attempt aggregate ceiling. Existing account quota snapshot is not live provider quota verification.

Current ordinary defaults remain OFF/FAKE/liveOFF. D07/D08 are unaccepted; full Agent E2E is NOT_RUN. The first local live request returned HTTP200 but failed response validation with unknown usage, so neither production readiness nor Vietnamese NLU quality is established.
