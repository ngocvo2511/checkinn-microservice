1. Introduction
   1. Purpose
This document serves as the comprehensive Software Requirements Specification (SRS) and Design Document for the Tripto project. Tripto is a hotel booking system that allows customers to search for hotels, view hotel details, book rooms, make payments, manage booking history, submit hotel reviews, and manage personal account information. The system also supports hotel owners in managing hotels, bookings, revenue, and customer reviews, while administrators can manage users, pending hotels, and system reports.
The primary purpose of this document is to define the software requirements and establish a clear design framework for the Tripto project. It provides a shared reference for developers, project managers, testers, documentation members, and other stakeholders involved in the software development lifecycle.
By describing the system requirements, use cases, business rules, user flows, and design considerations, this document helps ensure that the project is developed consistently with the expected functionality, technical constraints, and user needs. It also supports task planning, implementation, testing, deployment, and future maintenance of the Tripto
   2. Scope
The scope of this document covers both the functional and non-functional requirements of the Tripto project. It defines how the system operates from the perspective of customers, hotel owners, and administrators.
The functional scope includes major features such as user registration, login, forgot password, hotel search, room booking, payment processing, booking history, hotel reviews, personal information management, hotel owner review management, and administrative management functions.
The non-functional scope includes system performance, security, role-based access control, user interface behavior, system reliability, data validation, integration with external services, and deployment considerations.
Tripto is designed as a web-based hotel booking platform with separate workflows for different user roles. Customers interact with the system to search, book, pay, and review hotels. Hotel owners manage their hotel-related operations, including bookings, reviews, and revenue. Administrators manage system-level data and monitor platform operations.
   3. Intended Audiences and Document Organization
This document is intended for the teams and stakeholders involved in the development, documentation, testing, and evaluation of the Tripto project. Each audience uses this document for a different purpose, but all share the same goal: ensuring that the system is implemented according to the agreed requirements and design.


This document is intended for:
❖ Development Team: The development team uses this document as the main reference for implementing the Tripto system. It guides the design, coding, integration, and unit testing of customer, hotel owner, and administrator features.
❖ Documentation Team: The documentation team uses this document to understand system behavior, user flows, business rules, and feature scope. This helps them create clear and accurate user guides, technical documentation, and supporting materials for Tripto.
❖ UAT Team: The User Acceptance Testing team uses this document to validate the system from the end-user perspective. Their responsibility is to ensure that Tripto meets the expected business requirements, supports the defined use cases, and behaves correctly in real usage scenarios.






Below are the main sections of the document:
❖ 1. Introduction: This section provides the general introduction, purpose, scope, intended audiences, and document organization.
❖ 2. Functional Requirements: This section describes the system’s functional requirements in detail, including use cases and business flows.
❖ 3. Non-functional Requirements: This section describes non-functional requirements such as access control, security, interfaces, user experience, system performance, and reliability.
❖ 4. Other Requirements: This section describes additional requirements such as data management, audit considerations, backup, logging, and system constraints.
❖ 5. Appendixes: This section includes supporting information, diagrams, message codes, business rules, references, and other materials related to the Tripto project.

* Number of records: approximately 500,000 - 1,000,000 records in the first operating stage, including users, hotels, room types, bookings, payments, reviews, loyalty point transactions, and reports.
* Number of media files: approximately 50,000 - 100,000 files, mainly hotel images, room images, and support/policy documents.
* Average file size: approximately 1MB - 3MB per media file after compression.
* Data growth rate: approximately 50MB - 200MB per day, mainly from uploaded hotel/room images, booking transactions, payment records, reviews, and report data.


Level of availability
* The system is expected to achieve 95% availability.
* Tripto should remain available for customers to search hotels, view hotel details, create bookings, and make payments during normal operating periods.
* Temporary downtime may occur during scheduled maintenance, deployment, or infrastructure issues.


Usage frequency
* Tripto is used regularly by customers, hotel owners, and administrators.
* Customers may access the system at any time to search for hotels, make bookings, complete payment, view booking history, and submit reviews.
* Hotel owners use the system frequently to manage hotel information, check bookings, confirm onsite payments, update booking statuses, and view reviews.
* Administrators use the system to approve hotels, monitor platform data, and manage reports.
* The system should be deployed on a server capable of operating continuously, especially during peak booking periods. Maintenance and upgrades should be performed outside high-traffic hours.
