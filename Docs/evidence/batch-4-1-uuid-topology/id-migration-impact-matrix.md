## Producer/consumer ordering and compatibility

1. Approve exact conversions/exceptions and freeze generator/hash vectors first. Add boundary adapters preserving accepted string representation/tag numbers, not live producer rollover.
2. Build Booking aggregate/payment/refund typed entity+repository change coherently; build User Loyalty and Revenue adapters, Hotel eligibility/Media/User/Auth/Notification consumers and frontend string handling in same5A release candidate. No new code starts on old varchar database.
3. **5B** creates five **fresh owner databases** from exclusive V1 and launches candidate against those targets, validates all JDBC/JPQL/native/locks/recovery paths. Place untouched, city dataset identity gate explicit.
4. Batch6 stages projects privately, tests API/gRPC/RabbitMQ and degraded-network recovery, then concrete approved cutover quiesces old producers/consumers/jobs and drains/isolates pending commands/events/callback routes/cache. Do not run old String JDBC worker on uuid tables.
5. If rolling upgrade required, write explicit versioned/dual-compatible adapters and golden hash/receipt tests; wire string alone is insufficient. Preserve raw invalid events, command hashes/keys, event IDs/versions and original provider receipts. Legacy import requires owner-approved one-to-one mapping applied across references/integrations, never independent UUID regeneration.

## Exceptions and blockers

Regulations bigint IDs, ratePlanId String alias, opaque VNPay/transaction/evidence identifiers, command keys/hashes, numeric revisions/versions and mixed system actor/raw receipt contracts are not omitted conversions. Full registry in ID standard. Source tests/fixtures sometimes use short aliases; classify synthetic positive versus invalid tests before editing, never auto-rewrite provider values. No live value-validity claim. Provider settlement and changing business policy remain excluded.
