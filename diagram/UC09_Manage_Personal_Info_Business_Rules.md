# UC09 - Manage Personal Information Business Rules

## Use Case Check

The use case is partially correct against the current code. The authenticated profile APIs work for the user identified by the token, but the `/personal-data` frontend route is wrapped by `CustomerOnlyRoute`, which redirects `ADMIN` to `/admin/dashboard` and `OWNER` to `/host/dashboard`. Therefore, this screen currently supports the customer-facing personal data flow, while admin and owner access is not shown on this route.

The profile update part also does not update email. Email is loaded from the user account and displayed as disabled in the form; `UpdateProfileDto` and `handleSave()` only update full name, phone, gender, birthday, country, and address. Password is handled by a separate change-password endpoint within the same screen.

| Activity | BR Code | Description |
|---|---|---|
| (1) | BR1 | Personal Data Entry Rules:<br>The customer starts personal information management from the header/menu and is routed to the personal data page (View: `components/Header.tsx`, Route: `/personal-data`). |
| (2) | BR2 | Login Token Rules:<br>The personal data page must find [token] in local storage before rendering the page. Without [token], the user is treated as unauthenticated (View: `app/personal-data/page.tsx`). |
| (3) | BR3 | Unauthenticated Redirect Rules:<br>If [token] is missing, the page redirects the user to the home page and does not render personal information (View: `app/personal-data/page.tsx`). |
| (4) | BR4 | Role Guard Rules:<br>The customer-only route decodes [token] and checks [role] before allowing the page content to remain visible. This rule protects the customer profile route from admin and owner dashboards (Component: `CustomerOnlyRoute`). |
| (5) | BR5 | Dashboard Redirect Rules:<br>If [role] is `ADMIN`, the user is redirected to `/admin/dashboard`; if [role] is `OWNER`, the user is redirected to `/host/dashboard`. This means the current frontend route does not provide the admin/owner personal data flow (Component: `CustomerOnlyRoute`). |
| (6) | BR6 | Personal Data Display Rules:<br>After login and role checks pass, the system displays the personal data screen with header, sidebar, profile area, account tab, and security tab (View: `app/personal-data/page.tsx`, Component: `PersonalDataForm`). |
| (7) | BR7 | Profile Loading Rules:<br>The screen loads the logged-in user's profile before showing editable account data. The request uses [token] as a Bearer authorization header (Function: `fetchUserData()`, Endpoint: `GET /api/user/profile`). |
| (8) | BR8 | User Identity Rules:<br>The backend identifies the profile owner from [token], not from a user-selected id. The authorization header must start with `Bearer ` and is parsed into [userId] (Controller: `UserController.extractUserIdFromToken()`, Service: `JwtService.extractUserId()`). |
| (9) | BR9 | Profile Retrieval Rules:<br>The system retrieves the account and profile that belong to [userId]. Returned profile data includes [id], [fullName], [email], [phone], [gender], [birthday], [country], and [address] (Service: `UserService.getUserProfile()`). |
| (10) | BR10 | Missing Profile Rules:<br>If no profile exists for [userId], the system creates a default profile using the account username as [fullName] so the page can still load (Service: `UserService.createEmptyProfile()`). |
| (11) | BR11 | Profile Response Rules:<br>The backend returns profile data to the frontend. [email] comes from the user account and profile fields come from the user profile record (DTO: `UserProfileDto`). |
| (12) | BR12 | Loyalty Point Loading Rules:<br>After profile data is loaded, the screen loads point information using [data.id]. Loyalty loading is additional account information and does not block profile display if it fails (Frontend API: `loyaltyApi.getUserPoints()`, Endpoint: `GET /api/loyalty-points/{userId}`). |
| (13) | BR13 | Loyalty Point Response Rules:<br>The loyalty point summary contains [totalPoints], [usedPoints], and [availablePoints]. If no loyalty record exists, the backend creates a zero-point account before returning the summary (Service: `LoyaltyPointsService.getLoyaltyPoints()`). |
| (14) | BR14 | Profile Screen Rules:<br>The screen displays editable profile fields, disabled [email], loyalty point summary, and the password/security area. [email] is view-only in this use case because the frontend disables it and the update DTO does not include email (Component: `PersonalDataForm`, DTO: `UpdateProfileDto`). |
| (15) | BR15 | Action Selection Rules:<br>The user can either update account profile data or switch to the password/security tab to change password. These actions share the same page but use different backend endpoints (Component: `PersonalDataForm`). |
| (16) | BR16 | Editable Profile Field Rules:<br>The editable profile fields are [fullName], [phone], [birthday], [gender], [country], and [address]. [email] is not editable on this screen (Component: `PersonalDataForm`). |
| (17) | BR17 | Profile Submit Rules:<br>When saving profile changes, the frontend sends only editable profile fields. The request body excludes [email] and [loyaltyPoints] (Function: `handleSave()`). |
| (18) | BR18 | Save Token Rules:<br>The frontend checks [token] again before sending the save request. If [token] is absent, no profile update request is sent (Function: `handleSave()`). |
| (19) | BR19 | Save Authentication Message Rules:<br>If [token] is missing during save, the form displays MSG67 and stops the save action (Component: `PersonalDataForm`). |
| (20) | BR20 | Profile Update Request Rules:<br>A profile update request carries [fullName], [phone], [birthday], [address], [gender], and [country] for the logged-in user (Endpoint: `PUT /api/user/profile`). |
| (21) | BR21 | Update Identity Rules:<br>The backend again extracts [userId] from [token] before updating profile data. This prevents the frontend from choosing another user's profile to update (Controller: `UserController.updateProfile()`). |
| (22) | BR22 | Profile Update Field Rules:<br>Only non-null fields from the request are applied to the profile. [birthday] is parsed as a date when present; invalid date format is ignored by the current service logic (Service: `UserService.updateUserProfile()`). |
| (23) | BR23 | Profile Persistence Rules:<br>After applying allowed fields, the profile is saved to the user profile table. This persists the changed personal information for later reads (Repository call: `userProfileRepository.save(profile)`). |
| (24) | BR24 | Updated Profile Response Rules:<br>When saving succeeds, the backend returns the updated profile with [email] still coming from the user account and editable fields coming from the saved profile (Service: `UserService.updateUserProfile()`). |
| (25) | BR25 | Profile Success Message Rules:<br>After a successful profile update, the form displays MSG69 so the user knows the profile changes were saved (Component: `PersonalDataForm`). |
| (26) | BR26 | Profile Error Message Rules:<br>If profile loading or saving fails, the form shows an error message such as MSG68 or MSG70. The frontend uses the backend [message] when available and otherwise falls back to its default message (Component: `PersonalDataForm`). |
| (27) | BR27 | Security Tab Rules:<br>The password change flow starts when the user opens the password and security tab. This tab is part of the same personal data screen (State: `activeTab = "security"`). |
| (28) | BR28 | Password Input Rules:<br>The user must provide [currentPassword], [newPassword], and [confirmPassword] before changing password (State: `passwordData`). |
| (29) | BR29 | Password Client Validation Rules:<br>The frontend validates password fields before calling the backend. [currentPassword] is required, [newPassword] is required and must be at least 12 characters, and [confirmPassword] must match [newPassword] (Function: `handlePasswordChange()`). |
| (30) | BR30 | Password Validation Message Rules:<br>If client-side password validation fails, the form displays MSG71, MSG72, MSG73, MSG74, or MSG75 according to the invalid field and no backend request is sent (Component: `PersonalDataForm`). |
| (31) | BR31 | Password Token Rules:<br>After password fields pass client validation, the frontend checks [token] again before calling the change-password API. If [token] is absent, no backend request is sent (Function: `handlePasswordChange()`). |
| (32) | BR32 | Password Authentication Message Rules:<br>If [token] is missing during password change, the form displays MSG67 and stops the password change action (Component: `PersonalDataForm`). |
| (33) | BR33 | Change Password Request Rules:<br>A valid password change sends [currentPassword] and [newPassword] with [token] in the authorization header (Frontend API: `authApi.changePassword()`, Endpoint: `PUT /api/user/change-password`). |
| (34) | BR34 | Password Identity Rules:<br>The backend identifies the password owner from [token] before changing the password. The request does not accept a user id from the frontend (Controller: `UserController.changePassword()`). |
| (35) | BR35 | Password Server Validation Rules:<br>The backend checks that [currentPassword] matches the stored password and that [newPassword] is at least 12 characters. These checks protect the account even if client validation is bypassed (Service: `UserService.changePassword()`). |
| (36) | BR36 | Password Error Message Rules:<br>If [currentPassword] is wrong or [newPassword] is invalid, the password is not changed and the form displays MSG78, MSG19, or MSG77 depending on the backend response (Service: `UserService.changePassword()`, Component: `PersonalDataForm`). |
| (37) | BR37 | Password Persistence Rules:<br>When validation succeeds, [newPassword] is encoded before being saved. The system never saves the raw password value (Service: `UserService.changePassword()`, Repository call: `userRepository.save(user)`). |
| (38) | BR38 | Password Success Message Rules:<br>After the password is saved, the form clears password fields and displays MSG76 to confirm the password change (Component: `PersonalDataForm`). |
