# UC08 - Hotel Review Business Rules

| Activity | BR Code | Description |
|---|---|---|
| (1) | BR1 | Review Entry Rules:<br>The customer can start a hotel review from booking history only through a booking card that offers the write-review action. This action uses the selected [booking.id] and [booking.hotelId] to open the review page (View: `app/booking/history/page.tsx`). |
| (2) | BR2 | Review Eligibility Rules:<br>A booking is reviewable only when [booking.status] is `CHECKED_OUT` and [reviewedBookings] does not contain [booking.id]. This rule matches the UI condition that renders the write-review button (View: `app/booking/history/page.tsx`). |
| (3) | BR3 | Unavailable Action Rules:<br>If a booking is not completed or has already been reviewed, the write-review action is not available to the customer. The system prevents the use case from starting by hiding that action (View: `app/booking/history/page.tsx`). |
| (4) | BR4 | Review Navigation Rules:<br>When the customer starts the review, the system carries [bookingId] and [hotelId] to the review page so the review is tied to the correct stay and hotel (Route: `/reviews/new?bookingId=...&hotelId=...`). |
| (5) | BR5 | Review Context Rules:<br>The review page must have both review context and login context before displaying the form. It reads [bookingId] and [hotelId] from URL search params and reads [userToken] from local storage (View: `app/reviews/new/page.tsx`). |
| (6) | BR6 | Required Context Rules:<br>The review context is valid only when [bookingId], [hotelId], and [userToken] are present. Missing [bookingId] or [hotelId] means the page cannot identify the stay to review; missing [userToken] means the customer cannot submit a review. |
| (7) | BR7 | Context Error Rules:<br>If [bookingId] or [hotelId] is missing, the customer is sent back to booking history. If [userToken] is missing, the system asks the customer to log in using MSG60 (View: `app/reviews/new/page.tsx`). |
| (8) | BR8 | Booking Context Display Rules:<br>The review page loads the booking to show the stay being reviewed. The booking data provides [hotelName], [checkInDate], [checkOutDate], [roomType], and the confirmed [bookingId] for display (Frontend API: `bookingApi.getBooking()`, Backend: `BookingController.getBooking()`, `BookingService.getBooking()`). |
| (9) | BR9 | Hotel Context Display Rules:<br>The review page loads hotel details to show the hotel image and context. If hotel image loading fails, the page keeps a default image and continues; this does not block review submission (Frontend API: `hotelApi.getHotelById()`, Backend: `HotelController.getHotel()`, `HotelService.getDetail()`). |
| (10) | BR10 | Review Form Display Rules:<br>The review form is displayed only after valid booking context and login token are available. The form receives [hotelId], [bookingId], [userToken], and callback handlers (Component: `ReviewForm`). |
| (11) | BR11 | Review Input Rules:<br>The customer enters detailed ratings and review text. The review includes [staffRating], [amenitiesRating], [cleanlinessRating], [comfortRating], [valueForMoneyRating], [locationRating], [title], and [content] (Component: `ReviewForm`). |
| (12) | BR12 | Overall Rating Calculation Rules:<br>The overall [rating] is calculated automatically from the six detailed rating criteria. The form averages the values and rounds to one decimal place (Component: `ReviewForm`, State: `averageRating`). |
| (13) | BR13 | Review Submission Rules:<br>The customer submits the review by pressing the submit button. The submission sends the current [rating], detailed ratings, [title], [content], [hotelId], and [bookingId] if the form passes validation. |
| (14) | BR14 | Client Validation Rules:<br>The form validates review text and login state before calling the API. [title] and [content] must not be blank; [title] must have at least 5 characters; [content] must have at least 10 characters; [userToken] must exist (Function: `handleSubmit()`). |
| (15) | BR15 | Valid Input Rules:<br>Review input is valid only when all client-side validation checks pass. If any check fails, no API request is sent. |
| (16) | BR16 | Validation Message Rules:<br>Validation failures are shown directly in the form. Blank title/content uses MSG61, short title uses MSG62, short content uses MSG63, and missing login token uses MSG60 (Component: `ReviewForm`). |
| (17) | BR17 | Create Review Request Rules:<br>A valid review is sent as a create-review request. The request body includes [hotelId], [rating], detailed ratings, [title], [content], and [bookingId] (Frontend API: `reviewApi.createReview()`, Endpoint: `POST /api/v1/reviews`). |
| (18) | BR18 | Customer Identity Rules:<br>The customer identity is taken from the login token. The frontend decodes [userToken] to get [userId] and sends it in the `X-User-Id` header; the backend receives it as [guestId] (Frontend API: `reviewApi.createReview()`, Backend: `ReviewController.createReview()`). |
| (19) | BR19 | Server Validation Rules:<br>The backend validates the submitted review payload before creating a record. [hotelId] and [rating] are required; [rating] must be from 1 to 10; [title] must be 5 to 255 characters; [content] must be 10 to 5000 characters; detailed ratings must be from 1 to 10 when provided (DTO: `CreateReviewRequest`). |
| (20) | BR20 | Duplicate Review Check Rules:<br>A customer cannot review the same hotel for the same booking more than once. When [bookingId] is present, the system checks for an existing review with the same [hotelId], [guestId], and [bookingId] (Service: `ReviewService.createReview()`, Repository: `HotelReviewRepository.findByHotelIdAndGuestIdAndBookingId()`). |
| (21) | BR21 | Duplicate Result Rules:<br>A duplicate review exists when the duplicate check returns a review record. In that case, the new review must not be created. |
| (22) | BR22 | Duplicate Message Rules:<br>If a duplicate review is detected, the system returns an error and the form displays MSG65 or the backend error message (Service: `ReviewService.createReview()`, Component: `ReviewForm`). |
| (23) | BR23 | Review Publication Rules:<br>A non-duplicate review is saved as public immediately. The system maps the request into a review entity, assigns [guestId], sets [status] to `PUBLISHED`, and stores it (Service: `ReviewService.createReview()`, Mapper: `ReviewMapper.createRequestToEntity()`, Repository: `HotelReviewRepository.save()`). |
| (24) | BR24 | Created Review Response Rules:<br>After saving, the system returns the created review with identifiers, ratings, [title], [content], [bookingId], [status], and timestamps. Guest display information may be enriched when user-service is available (Mapper: `ReviewMapper.entityToResponse()`, Service: `ReviewService.enrichGuestInfo()`). |
| (25) | BR25 | Success Message Rules:<br>Successful creation is shown to the customer with MSG66. The success modal thanks the customer and lets them return to booking history (Component: `ReviewForm`). |
| (26) | BR26 | Success Redirect Rules:<br>After success, the customer is redirected back to booking history through the review page success callback (Function: `handleSuccess()`, Route: `/booking/history`). |
| (27) | BR27 | Public Visibility Rules:<br>Because the review [status] is `PUBLISHED`, it is included in public hotel review data. The hotel detail page loads review stats and recent reviews, and the created review can appear publicly in that review section (Frontend API: `reviewApi.getReviewStats()`, Backend: `ReviewController.getHotelReviewStats()`, `ReviewService.getHotelReviewStats()`). |
